# 持股追蹤、交易日誌與論點追蹤路線圖

規劃日期：2026-10-29。本文只記錄方向、邊界與驗收；以下新增能力均為待辦，未實作、未實測，本輪未啟用排程。

## 現況與目標

現有 `/taiwan` 已提供 Yahoo 日線快照、多頭／空頭／裁判報告、使用者模擬決策，並使用獨立的 `taiwan-exploratory.sqlite3`。目前未接券商帳戶或 Shioaji server；現有模擬紀錄不是實際成交，也不構成完整投資績效。

使用者選定的方向是：配合 Shioaji Pro 使用的持股追蹤、交易日誌與論點追蹤。規劃採用 **Custom App → 本機後端 → Shioaji server**，不宣稱已有 Shioaji Pro 原生面板外掛或已完成整合。

## 架構與共同邊界（待辦）

- [ ] Custom App 顯示持股、成交、日誌與論點；本機後端負責驗證、同步、快照與模型呼叫。
- [ ] 本機後端透過經驗證的 Shioaji server 介面取得資料；實際可用端點、登入方式與部署相容性需先確認。
- [ ] 初期僅暴露唯讀帳務功能，不新增下單或撤單端點。
- [ ] API key、憑證與帳戶識別留在後端；模型僅接收必要且去識別化的分析資料，不傳送帳號或其他帳戶識別。
- [ ] 每筆資料明確綁定帳戶與來源；查詢、匯出及同步皆隔離帳戶，帳戶切換不得沿用前一帳戶資料。
- [ ] 券商實際成交與既有模擬決策分表、分頁標示；不得以模擬決策補造實際成交。
- [ ] 數量統一保存明確的「股數」欄位及原始單位；一般交易、零股與張數轉換須驗證，不能直接假定回傳數值就是股數。
- [ ] 同步保存來源時間、取得時間、時區與完整性狀態；過期或不完整資料需清楚標示。

## P1：唯讀持股、成交同步與交易日誌（待辦）

- [ ] 先核對持股查詢、損益查詢與委託狀態更新的官方介面，再定義同步契約。
- [ ] 同步各帳戶持股及可取得的實際成交，保存每日持股快照；沒有新資料時標為缺漏，不複製昨日資料冒充今日快照。
- [ ] 以實際成交建立交易日誌，可由使用者補充交易理由、備註與附件，保留修改時間。
- [ ] `list_trades` 是當日／已知委託的狀態集合，不是完整歷史成交帳本；不可據此聲稱已取得所有歷史交易。
- [ ] 設計狀態補查、成交去重與對帳：冪等寫入，處理部分成交及後續狀態更新，避免同一成交重複入帳。
- [ ] 斷線與重啟後先補查、再對帳；無法補齊的期間保留缺口與原因，不靜默視為完整。
- [ ] 舊紀錄匯入格式、券商可回溯範圍及查詢限制待驗證；匯入資料標示來源，並與同步成交去重。
- [ ] 券商回傳的已實現損益須標示來源與查詢期間；交易費稅、入出金等現金流、除權息與其他公司行動未齊前，不宣稱自行計算的報酬率或損益代表完整帳戶績效。

驗收（待辦）：同一帳戶重跑同步不增加重複成交；兩帳戶同股票仍正確隔離；部分成交與零股股數可對帳；模擬資料不進入實際成交；斷線重啟能補查或明確報告缺口；每日快照與券商可核對資料一致，差異有紀錄。驗收需包含可控測試與經授權的實際唯讀核對，不能只用測試資料宣稱接通。

## P2：事件摘要與實質變化提醒（待辦）

- [ ] 建立可追溯的事件來源，保存網址、發布時間、取得時間與事件識別；目前尚未接入的新聞、財報等資料不得假定已有。
- [ ] 依使用者追蹤標的整理新增事件，將事實、推論與資料不足分開。
- [ ] 先用規則比對新事件、內容變更與既有摘要；只有實質變化才觸發摘要或提醒，重複、未變及非關鍵狀態保持安靜。
- [ ] 定義更正、撤回、重複新聞及來源失效處理；來源失效只標示資料問題，不推論公司狀況改變。

驗收（待辦）：相同事件重跑不重複通知；新增重要事件可追溯原文；更正內容保留版本；無實質變化不呼叫模型且不通知；摘要不將未驗證消息寫成已發生事實。

## P3：買進論點與多代理人增量複查（待辦）

- [ ] 原買進理由由使用者填寫，包含當時假設、觀察指標與失效條件；模型不得事後代填為使用者原意。
- [ ] 保存當時證據與論點版本，記錄可得資料時間；日後新資訊不得覆寫或回填成當時已知。
- [ ] 使用者可修訂目前論點，但歷史版本保持可追溯，區分原始理由、後續修訂及模型建議。
- [ ] 僅以新增事件、指標變化及受影響假設觸發多頭／空頭／裁判增量複查，引用證據差異並標出不確定性。
- [ ] 複查結果供使用者判讀，不能自動下單、改寫原始理由或將模型建議記成實際交易。

驗收（待辦）：能重建任一版本當時可用證據；原理由必須有使用者輸入來源；新證據只產生新版本或複查；無新增資訊不重跑；複查可逐項指出受影響假設、支持／反駁證據及缺資料。

## 資料表候選（待辦，名稱非既有實作）

| 候選資料表 | 用途與必要邊界 |
| --- | --- |
| `broker_accounts` | 後端帳戶映射與同步設定；不得傳送至模型 |
| `broker_fills` | 實際成交、來源識別、原始數量／單位及標準股數；帳戶內去重 |
| `position_snapshots` | 每日持股、來源時間、取得時間與完整性 |
| `sync_runs` | 同步範圍、游標、缺口、對帳結果與恢復狀態 |
| `trade_journal` | 成交關聯、使用者備註與修改紀錄；不混入模擬決策 |
| `thesis_versions` | 使用者論點、版本、指標與失效條件 |
| `evidence_snapshots` | 當時證據、來源與時間，供版本關聯 |
| `events` / `review_runs` | 事件版本、增量複查輸入、結果及成本 |

現有模擬決策保留在原探索資料邊界；新帳務資料的實際資料庫位置、備份及遷移策略需在實作前確認，避免污染正式研究資料。

## 成本、排程與啟動條件（待辦）

- [ ] 持股／成交同步與每日快照以程式處理，不需模型；模型成本僅由使用者手動要求或符合規則的實質新事件觸發。
- [ ] 模型執行前設定每次與每日預算、冷卻時間及相同輸入快取；記錄模型、token 與可得成本，超限停止並標示待處理。
- [ ] 排程依賴電腦、本機後端與所需 Shioaji 服務持續運行；關機或斷線會造成缺口，需由恢復流程補查。
- [ ] 本輪僅建立此路線圖，沒有啟用任何排程、券商連線、模型自動複查或通知。
